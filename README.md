# Ride Matching Service

## Overview

This project implements a Java backend service that matches ride requests with available drivers.

The service supports:

- Registering and updating a driver's location and availability
- Requesting a ride from a pickup location
- Allocating the nearest available driver
- Completing a ride and making the assigned driver available again
- Retrieving the nearest available drivers to a supplied location

All application data is stored in memory and is lost when the application restarts.

## Technology Stack

- Java 17
- Spring Boot
- Maven
- JUnit 5
- In-memory storage

## Functional Requirements

The service must:

- Register or update a driver's location and availability
- Allocate the nearest available driver to a ride request
- Mark an allocated driver as unavailable
- Return the allocated ride and driver details
- Complete an active ride
- Make the assigned driver available after ride completion
- Return the requested number of nearest available drivers
- Calculate distance using straight-line Euclidean distance
- handle concurrent requests safely
- Include unit tests for the required scenarios

## Project Structure

The project follows a layered structure:

- `domain` — driver, ride, location, and ride-status models
- `repository` — in-memory driver and ride storage
- `service` — business rules, allocation, completion, and concurrency handling
- `web` — REST controllers, DTOs, validation, and error handling

This section will be updated if the final implementation structure differs.

## API Endpoints

The final API contract, including request and response examples, will be documented after implementation.

Planned endpoints:

| Method | Endpoint | Description |
|---|---|---|
| `PUT` | `/drivers/{driverId}` | Register or update a driver |
| `POST` | `/rides` | Request and allocate a ride |
| `POST` | `/rides/{rideId}/complete` | Complete an active ride |
| `GET` | `/drivers/nearest` | Retrieve the nearest available drivers |

## Concurrency

Ride allocation must prevent the same driver from being assigned to multiple active rides.

The allocation, completion, and conflicting driver-update operations will use a shared lifecycle lock so that related driver and ride state transitions occur atomically.

The final concurrency implementation and trade-offs will be documented after implementation.

## Assumptions and Design Decisions

Current assumptions include:

- Driver IDs are supplied by the caller.
- Ride IDs are generated by the service.
- Coordinates represent points in a two-dimensional Cartesian plane.
- Distance is calculated using Euclidean distance.
- Equal-distance drivers are ordered by ascending driver ID.
- Application state is stored only in memory.
- A driver may be associated with at most one active ride.
