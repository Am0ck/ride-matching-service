# Ride Matching Service

## Overview

Ride Matching Service is a Java backend service that:

- registers drivers and updates their locations and availability;
- requests and allocates rides;
- selects the nearest available driver using Euclidean distance;
- marks allocated drivers unavailable;
- completes rides and restores driver availability; and
- returns the requested number of nearest available drivers.

All state is stored in memory. Drivers, rides, and the ride ID sequence are
lost whenever the process or container restarts.

## Technology Stack

- Java 17
- Spring Boot
- Maven with Maven Wrapper
- JUnit 5
- Spring MockMvc and Spring Boot integration testing
- In-memory, `HashMap`-based repositories
- Docker
- Postman collection

## Functional Behaviour

- Driver IDs are supplied by the caller.
- Ride IDs are generated by the service.
- New driver registration returns `201 Created`.
- Existing driver updates return `200 OK`.
- Ride allocation returns `201 Created`.
- Ride completion returns `200 OK`.
- Only available drivers are considered for allocation.
- Distance is Euclidean distance in a two-dimensional Cartesian plane.
- Equal-distance drivers are ordered by ascending numeric driver ID.
- Allocated drivers become unavailable.
- Completed rides restore their driver to available.
- A driver may have at most one active ride.
- A driver with an active ride may update location only while remaining
  unavailable.
- Attempting to make that driver available returns
  `409 DRIVER_HAS_ACTIVE_RIDE`.
- No available driver returns `409 NO_DRIVER_AVAILABLE`.
- Completing a missing ride returns `404 RIDE_NOT_FOUND`.
- Repeating completion returns `409 RIDE_ALREADY_COMPLETED` without another
  state change.
- The nearest-driver limit must be positive; no arbitrary upper bound is imposed.

## API Endpoints

| Method | Endpoint | Success status | Description |
|---|---|---|---|
| `PUT` | `/drivers/{driverId}` | `201` / `200` | Register or update a driver |
| `POST` | `/rides` | `201` | Allocate the nearest available driver |
| `POST` | `/rides/{rideId}/complete` | `200` | Complete an active ride |
| `GET` | `/drivers/nearest?x={x}&y={y}&limit={limit}` | `200` | Return nearest available drivers |

## API Examples

### Register or update a driver

Request:

```http
PUT /drivers/10
Content-Type: application/json

{
  "location": {
    "x": 1,
    "y": 0
  },
  "available": true
}
```

Response:

```json
{
  "driverId": 10,
  "location": {
    "x": 1.0,
    "y": 0.0
  },
  "available": true
}
```

The first registration returns `201 Created`; later updates return `200 OK`.

### Request a ride

Request:

```http
POST /rides
Content-Type: application/json

{
  "pickupLocation": {
    "x": 0,
    "y": 0
  }
}
```

Response:

```json
{
  "rideId": 1,
  "status": "ACTIVE",
  "pickupLocation": {
    "x": 0.0,
    "y": 0.0
  },
  "driver": {
    "driverId": 10,
    "location": {
      "x": 1.0,
      "y": 0.0
    },
    "available": false
  }
}
```

### Complete a ride

Request:

```http
POST /rides/1/complete
```

Response:

```json
{
  "rideId": 1,
  "status": "COMPLETED",
  "pickupLocation": {
    "x": 0.0,
    "y": 0.0
  },
  "driver": {
    "driverId": 10,
    "location": {
      "x": 1.0,
      "y": 0.0
    },
    "available": true
  }
}
```

### Retrieve nearest available drivers

Request:

```http
GET /drivers/nearest?x=0&y=0&limit=5
```

Response:

```json
{
  "drivers": [
    {
      "driverId": 10,
      "location": {
        "x": 1.0,
        "y": 0.0
      },
      "distance": 1.0
    }
  ]
}
```

Unavailable drivers are omitted. Results are ordered by distance, then by
ascending numeric driver ID.

## Error Responses

Errors use a structured response:

```json
{
  "timestamp": "2026-07-25T10:00:00Z",
  "status": 409,
  "code": "NO_DRIVER_AVAILABLE",
  "message": "No driver is currently available",
  "path": "/rides",
  "violations": []
}
```

The timestamp is generated at runtime.

| Code | HTTP status |
|---|---|
| `NO_DRIVER_AVAILABLE` | `409 Conflict` |
| `DRIVER_HAS_ACTIVE_RIDE` | `409 Conflict` |
| `RIDE_ALREADY_COMPLETED` | `409 Conflict` |
| `RIDE_NOT_FOUND` | `404 Not Found` |
| `VALIDATION_ERROR` | `400 Bad Request` |
| `INVALID_REQUEST` | `400 Bad Request` |
| `INTERNAL_ERROR` | `500 Internal Server Error` |

## Concurrency

`RideMatchingService` owns one non-fair `ReentrantLock`. The repositories
intentionally use ordinary `HashMap` instances, and all relevant repository
access follows the service-level lock protocol.

The lock protects:

- driver registration and update;
- nearest-driver selection;
- marking the selected driver unavailable;
- ride ID generation and ride creation;
- ride completion and driver reavailability; and
- copying available-driver snapshots.

Driver selection, state mutation, and ride creation occur in one critical
section, so two concurrent requests cannot allocate the same driver.

The nearest-driver query copies immutable driver ID and location snapshots
while holding the lock. It calculates distances, sorts, and limits the results
after releasing the lock.

A concurrency test verifies that simultaneous requests cannot allocate one
driver more than once.

## Assumptions and Design Decisions

- Driver IDs are positive `long` values supplied by the caller.
- Ride IDs are positive, monotonically increasing `long` values generated in
  memory.
- Coordinates represent a two-dimensional Cartesian plane.
- Distance uses Euclidean distance.
- Equal-distance ordering uses ascending numeric driver ID.
- Destination data is omitted because it does not affect the required matching
  workflow.
- Ride status contains `ACTIVE` and `COMPLETED`.
- State is stored only in memory.
- Restarting the service clears all drivers, rides, and the ride ID sequence.
- A driver may have at most one active ride.
- Repeated ride completion does not cause another state change but returns
  `409 RIDE_ALREADY_COMPLETED`.
- A nearest-driver limit must be positive; no arbitrary upper bound is imposed.

## Postman Collection

The collection is located at:

```text
postman/RideMatchingService.postman_collection.json
```

It covers the main API workflow, state transitions, business errors, and
validation cases.

- Set or retain `baseUrl` as `http://localhost:8080`.
- Run one iteration.
- Restart the application before each complete run because state is in memory.
- The workflow populates the `rideId1` and `rideId2` collection variables.
